# Commit

Crea un commit siguiendo estrictamente estas reglas.

## Reglas del mensaje

### Línea 1: título (máx 70 caracteres)
- Formato: `type(scope): description`
- El scope es opcional: `type: description` también es válido
- Tipos permitidos: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `ci`, `build`
- La descripción empieza en minúscula, sin punto final
- Modo imperativo: "add", "fix", "remove" (no "added", "fixed")
- **Siempre en inglés**

### Línea 2: vacía (separador obligatorio)

### Líneas 3+: cuerpo (opcional, cada línea máx 70 chars)
- Explica el **qué** y el **por qué**, no el **cómo**
- Usa viñetas con `-` si hay múltiples puntos
- Cada línea no debe superar 70 caracteres
- Si un punto es largo, córtalo en múltiples líneas
- **Siempre en inglés**

### Sin trailers
- NO agregar Co-Authored-By, Signed-off-by ni ningún trailer
- El mensaje termina con el cuerpo (o el título si no hay cuerpo)

## Tipo correcto según el cambio

| Tipo | Cuándo |
|------|--------|
| `feat` | Funcionalidad nueva para el usuario |
| `fix` | Corrección de bug |
| `refactor` | Cambio interno sin afectar funcionalidad |
| `perf` | Mejora de rendimiento |
| `docs` | Solo documentación |
| `style` | Formateo, espacios, imports (sin lógica) |
| `test` | Agregar o corregir tests |
| `ci` | Pipelines, workflows, GitHub Actions |
| `build` | Docker, Makefile, dependencias, scripts |
| `chore` | Mantenimiento que no encaja en otro tipo |

## Reglas de scope

- Usar cuando el cambio está acotado a un módulo: `fix(seo): ...`, `feat(content): ...`
- Scopes de este repo: `app`, `content`, `domain`, `features`, `ui`, `seo`, `a11y`, `perf`, `lib`, `config`, `deps`, `ci`, `ops`, `docs`, `test`
- No usar scope si el cambio toca múltiples módulos

## Proceso

1. Ejecuta `git status` y `git diff --staged` para ver los cambios
2. Si no hay nada en staging, usa `git add` de los archivos relevantes (NUNCA `git add -A` ni `git add .`)
3. Analiza TODOS los cambios en staging y elige el tipo correcto
4. Si los cambios son de naturaleza distinta, sugiere separarlos en múltiples commits
5. Redacta el mensaje siguiendo las reglas (en inglés)
6. Ejecuta el commit con HEREDOC:

```bash
git commit -m "$(cat <<'EOF'
type(scope): short description

Optional body explaining context
and motivation for the change.
EOF
)"
```

7. Ejecuta `git status` para verificar que el commit se creó

## Ejemplos buenos

```
feat(content): add eighth sponsor to the roster

- Register the logo in src/content/sponsors.ts
- Validate the asset path against the content schema
```

```
fix(seo): use the event time zone for the sitemap date

Parsing the ISO date as UTC shifted every date one day
back when rendered from a UTC server.
```

```
build: add load testing scripts
```

## Qué NO hacer

- NO agregar Co-Authored-By ni ningún trailer
- NO escribir "autogenerated", "generated with" ni mencionar herramientas
- NO poner punto final en el título
- NO superar 70 caracteres en ninguna línea
- NO mezclar cambios de distinta naturaleza en un commit
- NO usar `git add -A` ni `git add .`
- NO hacer commit de archivos con secretos (.env, credentials, API keys)
- NO hacer amend a menos que el usuario lo pida explícitamente
- NO escribir el mensaje en español
